

**结论**
- 核心路线选型：`RAG-first + typed document graph + approval workflow`
- 原来的 QT Wiki 可以保留两部分：多格式解析能力、人工审批思想
- 原来的 QT Wiki 不适合作为主模型的部分：`overview/entity/concept/comparison` 这套 page-first 设计，不该再作为主交付物
- 你的主交付物应该改成：`法规 -> 内部主文档 -> 附件文档 -> 章节 -> 证据片段`
- Wiki 页面可以保留为派生产物，用于“审批通过后的漂亮展示、总结页、slides 输入”，而不是主存储

如果只让我给一句判断：保留原项目的解析层，重做查询层和数据模型，产品主线从“写 wiki”改成“法规导航与章节证据问答”。

**产品设计**
产品定位不要叫“Wiki”，而应该更像“Regulation Navigator”或“法规落地工作台”。用户打开系统后，不是先看到一堆页面，而是先看到法规、相关内部文件、附件、章节和证据。

核心对象建议固定成这 5 类：
- 外部法规文档：法规、规范、指南
- 内部主文档：PEP、SOP、WI、流程主文档
- 内部附件文档：模板、记录表、附录、表单
- 章节对象：文档内按章拆分的结构节点
- 证据片段：可回溯到页码、段落、表格、图的最小引用单元

MVP 的核心价值要非常单一：
- 给定一个法规，系统能告诉用户有哪些内部文档与它相关
- 用户能展开某个内部文档，继续看到对应的章节
- 用户能继续展开章节，看到原文证据
- 用户提问时，答案能明确区分：
  - 法规要求
  - 内部落实方式
  - 附件/模板承接位置
  - 证据出处

LLM 交互不要真的存“自由文本 CoT”，而要做成“结构化推理编排”。推荐 5 段式：
- `Doc Classifier`：先判断文档类型，是外部法规、内部主文档还是附件
- `Section Resolver`：把问题先落到法规章节，再落到内部文档章节
- `Relation Retriever`：找法规与内部文档、主文档与附件之间的候选关系
- `Answer Composer`：生成回答，并强制拆成“法规要求 / 内部文件 / 章节证据 / 不确定点”
- `Suggestion Generator`：生成推荐问题、比较视图、HTML 摘要卡

这套“CoT”建议只保存结构化字段，不保存模型的自由思维文本。你真正要存的是：
- 用户问题意图
- 识别出的法规对象
- 命中的文档列表
- 命中的章节列表
- 最终引用的证据片段
- 置信度和待审点

UI 我建议做成 4 个主界面，而不是一个大而全的聊天页：

1. 法规中心
- 左侧是法规列表和筛选
- 中间是法规详情卡，显示版本、适用范围、状态、关联内部主文档数
- 下方是“已关联内部文档”列表，按主文档和附件分组
- 这是首页，也是最核心页面

2. 法规详情页
- 左栏：法规章节树
- 中栏：命中的内部主文档和附件树
- 右栏：章节证据抽屉，显示页码、表格、段落引用
- 顶部 Tab 建议是：`总览 / 相关文档 / 章节映射 / 问答 / 审批记录`
- 这页最能体现你的核心产品价值

3. 智能问答页
- 不做纯聊天，而做“带结构结果的问答”
- 回答区上方先给一个结论卡
- 下方固定展示：
  - 相关法规章节
  - 相关内部文档
  - 相关附件
  - 证据引用
- 右侧放推荐问题，比如：
  - “这条法规在内部由哪些 SOP 承接？”
  - “这个章节对应哪些模板？”
  - “有哪些法规要求还没有内部文档覆盖？”

4. 审批工作台
- 审批对象不是 wiki 页面，而是：
  - 文档身份
  - 主文档/附件归属关系
  - 法规到内部文档的关键映射
  - 低置信度章节关系
- 现有的 workbench 风格可以保留，但内容对象要换掉

Phase 2 的 wow moments 建议放这些，而不是一开始就做复杂图谱：
- 推荐问题卡片
- 法规覆盖矩阵
- 章节对章节映射视图
- 自动生成漂亮的 HTML 摘要页
- 自动把表格、流程图、模板抽出来做多模态展示
- 一键生成“法规落地简报”或框图

**开发方案**
技术架构我建议继续用现有 Python 主体，但把系统拆成 6 个明确模块：

- `Parsing Layer`：复用现有 PDF/DOCX/XLSX/PPTX 解析能力
- `Document Registry`：管理文档身份、版本、主文档/附件关系
- `Section Index`：管理章节树、章节 chunk、页码锚点、表格锚点
- `Relation Layer`：管理法规到文档、文档到附件、章节到章节的关系
- `Retrieval Layer`：做混合检索，先 metadata/filter，再 vector，再 rerank
- `Answer Orchestrator`：负责问答、推荐问题、多模态输出、HTML 产物

数据存储不要一上来上图数据库。你的第一阶段最合适的是“关系型数据库 + 向量索引 + 原始文件存储”：
- 原始文件：本地文件系统、SharePoint、Blob 都可以
- 结构化元数据：`PostgreSQL`
- 向量检索：优先 `pgvector`
- 如果你们 Azure 生态已经很成熟，也可以改成 `Azure AI Search + PostgreSQL`
- 不建议 MVP 就上 Neo4j，复杂度高，收益不够直接

推荐的核心表结构：
- `documents`：文档主表，含 `doc_type`、`authority_level`、`parent_document_id`
- `document_versions`：版本信息
- `sections`：章节树，含 `path`、`level`、`page_start/page_end`
- `chunks`：章节内可检索片段
- `tables` / `figures`：表格和图对象
- `document_relations`：`implements`、`attachment_of`、`references`、`interprets`
- `section_relations`：章节到章节的映射
- `approvals`：审批记录
- `query_logs`：问答轨迹
- `generated_assets`：HTML、框图、导出内容

检索链路建议这样做：
- 第一步：识别用户是在问哪条法规、哪个内部流程、哪个附件
- 第二步：按文档类型做 metadata 过滤
- 第三步：优先按章节级召回，不要直接按整篇文档召回
- 第四步：用 reranker 重新排序章节和证据片段
- 第五步：生成答案，并把法规章节、内部文档章节、附件证据分别列出来

你这个项目最重要的不是“回答得像不像”，而是“能不能把答案拆成受控证据结构”。所以回答输出 contract 我建议固定为：
- 结论
- 涉及的法规
- 涉及的内部主文档
- 涉及的附件
- 命中的章节
- 证据片段
- 不确定项
- 建议下一步问题

对现有仓库的改造建议很明确：
- 直接复用：解析器、canonical 文档结构、审批思路
- 局部改造：ingest 流程，把候选对象从 wiki page 改成 document/section/relation candidate
- 重点重写：query 主线，不再走全 wiki 上下文
- 降级为派生能力：wiki publish、overview/entity/concept 页面生成

项目分期建议这样排：

1. Phase 1，先做可用闭环
- 文档类型识别
- 多格式解析
- 按章节切分
- 法规详情页
- 相关内部文档与附件展开
- 章节级引用展示

2. Phase 1.5，补齐问答主线
- 结构化问答输出
- 推荐问题
- 审批工作台
- 关键关系人工确认

3. Phase 2，做 wow moments
- 覆盖矩阵
- 章节映射图
- 多模态摘要
- 漂亮 HTML 页面
- slide/diagram 输出

最后给你一个最直接的产品定义版本，你可以直接拿去跟用户或团队对齐：

“这不是一个先生成 wiki 页面、再让人去搜的系统；这是一个以法规为入口、以内部文档和附件为承接、以章节和证据为检索单元、以受控审批为边界的法规导航型知识平台。”
